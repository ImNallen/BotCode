# UI baseline

Bot Code renders the T3 Code interface for every workflow it implements. The reference is T3 Code v0.0.45 (`pingdotgg/t3code` tag `v0.0.45`, commit `6c8fed35d`), the build in the installed desktop app. T3 Code is MIT licensed. Ported files name their source in a one-line header.

## Styles come from T3, not from a lookalike

`src/t3-theme.css` is T3's `apps/web/src/index.css`, copied verbatim. Regenerate it with `scripts/port-t3-theme.sh <t3code-checkout>`. Tailwind v4 compiles it through `@tailwindcss/vite`, so components use T3's own utility classes and tokens: `bg-sidebar`, `text-secondary-label`, `--chat-max-width`, `alert-glass`. `src/styles.css` imports the theme and holds the only Bot Code overrides: root typography, which T3 sets from JavaScript, and the macOS traffic-light inset.

`src/ui/controls.tsx` copies T3's `buttonVariants` and `toggleVariants` tables and the select trigger and item classes. Components copy T3's class strings literally. A hand-written approximation drifts the first time T3 changes a token. A copied class string can only drift when the copy is stale.

## Layout

The shell matches T3's desktop app:

- A 256px left sidebar, resizable from 208px and collapsible with Command+B. It holds the brand row, thread search, T3's project filter, **Add project**, **New thread**, and T3's Pinned section, Active list, Snoozed shelf and Settled shelf across every repository. Pinned threads show as cards at the top, newest pin first. They have no header, because T3 labels them only while dragging. The pin icon on a pinned card unpins it. Active threads show as cards below them, newest activity first. Hovering a card shows a clock button and **Settle** in place of its time, except while an approval waits. The clock opens T3's snooze presets: In 1 hour, In 3 hours, This evening while 6 PM is more than an hour away, Tomorrow at 9 AM, and Next week on Monday at 9 AM. Right-clicking any thread opens T3's thread menu with Pin or Unpin, Settle or Un-settle, and a Snooze submenu with the same presets, or Wake when the thread is snoozed. The **Snoozed** shelf appears above Settled while any thread is snoozed. Its slim rows show the soonest wake first, the time left, such as "2h", and a **Wake thread now** button on hover. It starts collapsed as "Snoozed (n)" and shows only the open thread's row until expanded. A snoozed thread comes back when its wake time passes, without a reload. It comes back early when an approval arrives, or when a turn completes or fails after the snooze. A pinned thread keeps its pin while snoozed and comes back into Pinned. The **Settled** shelf sits at the bottom of the list as slim rows, most recently settled first, with a dimmed badge, the title, the settled age, and an **Un-settle** button on hover. It starts collapsed as "Settled (n)" and shows only the open thread's row until expanded. Expanded, it shows 10 rows and then **Show more** in steps of 25. Both shelves remember their state on this device. Search shows every matching snoozed and settled row. Settling or snoozing the open thread opens the next card, or a new draft in its project when none is left. Command+Shift+S settles or un-settles the open thread in place, and Command+Shift+P pins or unpins it in place. Pinning clears a settle or a snooze. Settling clears a pin or a snooze. Snoozing keeps the pin or settle. A thread settles by itself after its project's auto-settle limit without activity, 3 days by default, unless the user un-settled it or it is snoozed. An idle pinned thread settles by itself too and loses its pin, as in T3. Pinning a settled thread un-settles it, so it stays pinned until its next activity and does not settle by itself before then. A new prompt clears the snooze and returns a settled thread to the active list. It keeps a current pin but does not restore a pin that settling removed. A new approval also returns a settled thread. Bot Code leaves out T3's Working shelf, drag and drop, the Custom snooze time, and the Woke indicator. The filter is a searchable popup under the search field. It lists **All projects**, then **No project**, then repositories by name. Choosing a project shows only its threads and its badge replaces the folder icon. The choice persists on this device and falls back to all projects when that project is gone. While a project is chosen, **New thread** opens that project's draft. Each project row has a settings button, and right-clicking the row also opens that project's Project settings page. A fixed bottom bar contains the 32px Settings gear and T3's **Usage** button. Settings replaces the sidebar list with search and category navigation. On Settings or Usage, the bottom bar becomes Back.
- A 52px header with the repository badge, the thread title, T3's Git actions control, and fixed terminal and right-panel toggles.
- A centered 48rem conversation column. The composer floats over the bottom of the timeline. A new thread centers the composer under "What should we build in {repository}?", and that repository name is the repository picker.
- An optional right panel, 540px by default, with Terminal, Files, file, Diff, Pull requests, and pull request tabs. With no tab open, it shows T3's **Open a surface** launcher, where each row's letter opens it: **T** for Terminal, **F** for Files, **D** for Diff and **P** for Pull requests.
- An optional terminal drawer at the bottom of the conversation column. It spans the timeline and composer but not the right panel.

The terminal drawer follows T3's thread terminal drawer and renders with T3's Ghostty terminal. The header's terminal toggle, left of the right-panel toggle, and Command+J open and close it. Opening focuses the terminal, and closing returns focus to the composer. The drawer is 280px tall by default and resizes from its top edge between 180px and 75% of the window. Each thread has its own terminals, and a repository draft has its own. A thread without a project has no toggle until its first message creates its folder. A single terminal shows T3's floating toolbar with **Split Terminal Horizontally**, **Split Terminal Vertically**, **New Terminal** and **Close Terminal**. Two or more terminals show T3's tab sidebar with Single, Side by side and Stacked groups of up to four terminals. Closing a terminal asks for confirmation and stops its process. When the process exits, the terminal prints "[terminal] Process exited" and its tab closes. A terminal that cannot start, such as one in a removed worktree, prints the reason. Switching threads detaches the terminals. Their shells keep running and replay their output when the thread opens again. The open state, height, terminals and splits persist on this device. After a restart, each terminal starts a new shell. Command+K or Control+L clears the terminal. Option and Command with the arrow keys move by word and to the line ends, and Command+Backspace deletes to the line start. Selecting text offers **Copy**, and right-clicking offers **Copy** and **Paste**. On macOS, Option types the character it composes, such as $ or @ on Swedish layouts, as Ghostty does by default, and Command chords other than copy, paste and the terminal shortcuts never reach the shell. Clicking a web link opens it in the system browser. Clicking a path that matches a file in the checkout opens it in the right panel's file tab. A terminal can also open as a right-panel tab from the launcher's **Terminal** row, the **+** menu, or **T** while the launcher shows. A no-project draft shows the row disabled with T3's reason. The tab is titled with its active terminal, such as "Terminal 2", and shows T3's terminal icon. It fills the panel with the same toolbar and tab sidebar as the drawer, holds up to four terminals in one split, and Command+N in it opens another terminal tab. Terminal numbers are shared between the drawer and the panel, so a new terminal takes the lowest free number. Closing the tab asks for confirmation and stops every terminal in it, and closing or exiting its last terminal removes the tab. Each thread keeps its own terminal tabs: switching threads removes them from the panel without stopping their shells, and returning brings them back with replayed output. Only the active tab's terminals stay attached. Text uses T3's terminal font stack at the code font size, with colors from T3's terminal theme variables. Bot Code leaves out T3's **Add to chat** and terminal context in the composer, the in-app preview for links, subprocess names in tab labels, hidden drawers kept mounted for recent threads, and terminal history across app restarts.

A thread can also start without a project, as in T3 commit `6b286ae8a`. A launch with no projects opens that draft directly, a repository draft offers **or start without a project** under its heading, and Command+Option+N opens the same draft. That draft asks "What should we work on?" and moves the picker, which reads **No project**, to the line below. Each of these threads runs Codex in its own plain folder under `scratch` in the data directory, named from the date, the first words of the prompt, and a short id. They show T3's gray dashed message icon and have no workspace selector, branch picker, or Diff tab. Bot Code creates the **No project** workspace the first time it is needed, and the sidebar's project filter then lists it first. The option is absent when the data directory sits inside a Git work tree. In that case, or when creating the workspace fails, the empty window offers **Add project** instead.

Appearance follows the system by default. The local preferences owner in `src/settings/preferences.tsx` applies the system, light or dark choice, and the prompt and code font sizes. The macOS window keeps an overlay titlebar with native traffic lights at `{16, 28}`. That centers them in the 52px header, level with the sidebar toggle, as T3's Electron position `{16, 19}` does. Elements that carry T3's `drag-region` class also carry `data-tauri-drag-region="deep"`, which gives Tauri the same rule: the subtree drags and clickable children opt out.

## Thread lifecycle

The thread menu ports T3 v0.0.45 `threadActionMenu.logic.ts` and `Sidebar.tsx`. After the arrangement actions, it shows **Rename thread**, the **Copy** submenu with **Path**, optional **Branch**, and **Thread ID**, **Archive thread**, and destructive **Delete**. Rename replaces the card or shelf title with T3's inline input. Enter or blur saves a trimmed nonempty title. Escape cancels. A failed save keeps the editor and shows the error. The input and rename switching stay disabled while a save is pending. Copy reads the thread's checkout path and branch, or the local repository path and branch. Clipboard failures appear in the sidebar.

Archive hides an idle thread from every ordinary list, search, count, and shortcut target. The open thread moves to the next card or its project's draft after the operation succeeds. Archive stores its former pin, settle, kept, or automatic placement and clears its snooze. **Settings > Archived** ports T3's grouped project rows, archive and creation ages, **Unarchive** button, and context-menu **Unarchive** and **Delete**. It respects the settings project scope and appears in settings search. Its summaries come from persisted thread metadata, so an unavailable repository does not hide its archives. Unarchive restores the saved placement. An automatically managed thread with old activity can settle again after restoration.

Delete uses T3's confirmation text, "This permanently clears conversation history for this thread." It stops all terminals owned by that thread and removes its history, submission receipts, and pull request memberships. Shared pull request records, operations, and project review decisions remain. A running or pending conversation or an operation holding the same checkout blocks deletion before it changes anything. Successful deletion of the open thread follows the same forward navigation as archive, provided that thread is still open.

Storage adds T3's default-off **Delete worktrees with deleted threads** row and description. With it enabled, deletion tries `git worktree remove` without force after checking ownership, location, branch, changes, and ignored files. Dirty, shared, locked, unsafe, or refused worktrees remain, and a neutral status gives the reason. Deletion never removes the branch, local repository, or scratch folder. It does not queue past deletions for later cleanup. If the database fails after Git removal, the visible conversation remains and the existing missing-worktree restore path can recreate its checkout on the next message.

## Command palette

Command+K opens the palette from chat, Settings, Usage, and the right panel. A focused terminal keeps Command+K for clearing its output. The palette ports T3 v0.0.45's `CommandPalette`, `CommandPaletteContent`, `CommandPaletteResults`, `commandPaletteBus`, and command, autocomplete, and keycap class strings. Its modal sits near the top of the window with T3's search input, grouped rows, highlighted selection, shortcut labels, and Navigate and Close footer. The background cannot take focus or run shortcuts while the palette is open.

An empty query shows actions and up to twelve recent threads. Search includes titles from every project's nonarchived summaries, including snoozed and settled threads. Message search reads prompts and user and assistant text only from snapshots already loaded in this session. It shows that coverage in the palette and does not fetch every thread's history. Queries ignore case, accents, and repeated whitespace. Every query word must match. Title matches rank before message matches, and recent activity breaks ties. A leading `>` searches actions only.

The action table owns labels, eligibility, execution, and shortcut descriptors. Both the palette and `src/lib/shortcuts.ts` read it. Working actions include new thread, new thread without a project, open Settings, toggle sidebar, terminal drawer and right panel, pin or unpin, settle or un-settle, snooze presets or wake, rename, copy path, optional branch and thread ID, archive, delete, and archived-thread restoration. Pin and settle use the same in-place operation as their shortcuts. Snooze, archive and deletion keep the existing successful forward navigation. Deletion keeps its native confirmation. Archived threads have their own restoration submenu and remain absent from ordinary search. Core refusals still report concurrent checkout operations that summary metadata cannot prove available.

Arrow keys navigate and Enter runs the highlighted result. Escape closes the palette before an underlying Settings search or page consumes it. Backspace on an empty submenu query returns to its parent. Ordinary dismissal restores the control that opened the palette, with the composer as a fallback; actions such as rename, open Settings and toggle terminal focus their own control. Opening requests cancellation of an existing in-app dialog through its normal handler. If an active operation refuses cancellation, the palette opens with a wait message and no executable results until dismissed. Rename reveals its existing inline editor even when the sidebar is collapsed or filtered. Bot Code omits T3's unsupported file and project-content search, theme editor, cloning, and environment actions.

## Only working controls appear

Every repository turn captures the checkout before Codex starts and after it finishes. T3's changed-files card appears below the turn with its file tree, line counts, folder expansion, and **Open diff**. Clicking a file opens that turn's diff and reveals the file. The Diff scope menu keeps Working tree, Unstaged, and Staged, and adds T3's **Latest turn** and **Turn** submenu. Choosing Turn 2 compares only that turn's two checkpoints, regardless of later changes. Missing checkpoints show their reason instead of a diff against HEAD. Threads without a project have no checkpoint diff.

Hovering a user message reveals T3's **Edit from here** button beside Copy. It is disabled while the conversation or its checkpoint capture runs. The dialog copies T3's layout and offers **Cancel**, **Revert files too**, and **Revert and keep changes**. Both rewind the timeline to before that message and return its prompt and images to the composer, preserving current unsent input. Pending image staging or the 100-image limit defers the whole recovery and explains how to make room. Original recovered images survive restart until an accepted send. Bot Code continues on a new native Codex thread containing only the earlier conversation, and the dialog says so. Revert and keep changes keeps the current checkout contents. Revert files too restores tracked and non-ignored files, removes later non-ignored files, preserves ignored files, and leaves restored changes unstaged when HEAD exists. Its confirmation says that the current checkout changes will be replaced. The file choice is absent when no before checkpoint exists, the thread has no project, or its worktree has been removed.

The core refuses either choice while a turn, Git action, branch switch, checkpoint capture, or cleanup holds the checkout. Preflight refusal releases the checkout without changing its files or conversation. A failure after preparation keeps a **Retry revert** control above the composer. Retry continues the saved operation and offers only its original mode. The operation and prompt survive restart. Ignored file collisions and unsafe nested repositories, submodules, or ignore-rule changes show a refusal. A successful revert does not send the returned prompt.

The composer accepts images as T3's does. Paste one into the prompt or drop one on the composer, which shows T3's drag-over ring. Each image appears as T3's 64px thumbnail above the prompt with a **Remove** button, and Send waits until every image is stored. Bot Code accepts PNG, JPEG, GIF and WebP up to 10 MiB each and 100 per message, and a message can be images alone. An image-only first message titles the thread "Image: {name}", as in T3, and keeps the temporary worktree branch because the name generator reads no images. The user message in the timeline shows T3's two-column image grid above its text. Bot Code leaves out T3's expanded image preview, other file kinds, video, HEIC conversion, dropping on sidebar rows, and the whole-column drop target. A file dropped anywhere outside the composer does nothing. The composer has model, reasoning effort, and access-mode menus backed by per-thread Codex settings and the live model catalog. Left of Send or Stop, T3's context window meter appears once Codex reports the thread's token usage. Its ring fills with the share of the context window in use and turns red above 90%. Hovering or focusing it shows a card with the percentage, the used and maximum tokens, the total processed, and T3's note that context compacts automatically. The card does not take focus. General > Application has T3's **Context window indicator** switch, which is on by default. Restore defaults turns it back on. The context strip under the composer starts with T3's workspace selector on a new thread: **Current checkout** or **New worktree**. Once a thread exists, the left side shows a fixed **Local checkout** or **Worktree** label. The right side is T3's branch picker in every state. A worktree draft uses it to choose the base, which defaults to the repository's default branch, and its **Start from origin** switch. The trigger then reads "From origin/{base}" or "From {base}". Elsewhere, picking a ref switches the checkout's branch, and a typed name that matches no ref offers **Create new ref**. Branches checked out in another worktree are disabled. Bot Code leaves out T3's pull request badge, pull request checkout, and a general worktree reuse picker. Plan implementation can reuse its source checkout. Sidebar rows of worktree threads show T3's worktree icon and the worktree branch. A new worktree starts with a temporary `botcode/<random>` branch and a matching random folder. Its first accepted message generates a short branch name in the background using the selected Codex model. Bot Code applies the name after that turn releases the checkout. The folder stays in place, and the sidebar and branch picker refresh together. Naming keeps the branch the worktree started from as the pull request base. Local checkouts, manually named branches, and later messages do not start naming. A switch, Git action, later message, cleanup, project removal, or provider loss cancels pending naming. Generation errors and existing upstream or remote tracking refs leave the temporary branch in place. A name collision adds the original random suffix without overwriting another branch.

Follow-up input ports T3 v0.0.45's `queuedMessageStore`, `QueuedMessageSender`, `ComposerPrimaryActions`, and dashed `MessagesTimeline` rows. Send stays beside Stop when text or images are ready, including during approvals. General > Application has T3's **Follow-up behavior** menu with **Queue** and **Steer**, default Queue. Enter uses that choice while a turn runs. Queue captures the prompt, staged images, and current send settings. The first row's **Send now** steers the exact running turn, or starts a turn when idle. Later rows cannot overtake it. Connecting input waits in the queue. Approvals block delivery while the composer stays editable.

Queued rows appear under the timeline with T3's dashed border and icon actions. Automatic sends wait for successful completion, saved final checkpoints, resolved approvals, and confirmed delivery. Failed, interrupted, or lost turns hold the queue for explicit Send now. Stop holds it before interruption and restores every unsent row in order beside existing draft input. Remove restores one row. Staging or the image limit leaves recovery held and visible. In-flight rows cannot be recalled. An uncertain IPC response shows **Check delivery** for the same operation. Queues survive thread switches and send from the application root, including hidden threads. They live in memory and disappear on renderer reload or app exit. Accepted input persists in conversation history.

Steering appears as an ordinary user bubble inside the existing turn, visible outside completed work folds. It offers Copy only. A failed or uncertain steer keeps its delivery explanation in that bubble. The original prompt's Edit from here removes the entire turn including its steers, and restores only the original prompt and images. Opening rewind holds and restores unsent queued input. Archive, delete, and project removal require removing queued rows first.

Sending exactly `/usage-limits`, in any letter case, opens T3's **Usage limits** notice above the composer and sends nothing to Codex. It works on a draft and while a turn runs. The notice shows the Codex plan, then each limit window with its remaining share, the even-spending mark, pace and time to reset, as of the moment it opened. Dismissing it, a new turn, a new approval or another thread closes it. The **Usage** button opens T3's Usage page with only its limits section, showing the same windows for the Codex account. **Refresh** reads the limits again. Codex also pushes changes while turns run. Back or Escape returns to the conversation. Bot Code leaves out T3's **Compact context** button, reset credits, token and cost history, and multiple accounts.

A thread in a repository checkout shows T3's Git actions control at the right of the header. Drafts, threads without a project, and removed worktrees show none. Its quick-action button runs the step T3 picks for the branch, such as **Commit, push & PR**, **Commit & push**, **Push & create PR**, **Create PR**, **Pull**, or **View PR**, and shows only its icon when the header is narrow. The chevron menu lists **Commit**, **Push**, and **Create PR** or **View PR**. A disabled button or item explains itself on hover. An action that commits opens T3's commit dialog first. It shows the branch and the changed files with their line counts, shows an editable generated commit message with an optional message field, and offers **Cancel** and a button named for the whole action, such as **Commit** or **Commit, push & PR**. Command+Enter starts it. The message field uses T3's "Commit message (optional)" label and "Leave empty to auto-generate" placeholder. Generation starts when the dialog opens and does not change the real Git index. A loading note keeps editing and submission available, and a late result preserves any text the user has edited, including an intentional blank. The visible generated message is the user-approved message when submitted. A blank submission generates afresh from the actual staged diff after the action passes preflight. Closing the dialog, changing threads, or submitting cancels its preview. A failed preview explains how to enter a message or retry by leaving it blank. A failed automatic commit asks for a typed message and offers **Commit** to reopen the dialog. Create PR generates a title and Markdown body from the branch's commits and diff against its recorded base, after any commit and push in the action. A failed generation uses GitHub CLI's commit-based title and body and reports that fallback in the result toast. On the default branch, a push or a pull request first asks for confirmation with **Abort** and **Continue**. While the action runs, a toast below the header names the current step. The finished toast shows the result and offers **View PR**, **Push**, or **Create PR** when one applies. When a step fails after an earlier step landed, the toast keeps what landed, such as "Committed abc1234", and names the step that failed. A Codex turn in the same checkout disables the control, and Bot Code refuses a prompt or a branch switch there while a Git action runs. Pull requests need the GitHub CLI signed in. Without it, commit and push still work, and the pull request items say what is missing. Bot Code leaves out T3's source control writing-style settings, file selection in the commit dialog, **Commit on new branch**, the feature-branch choice in the default-branch confirmation, **Publish repository**, providers other than GitHub and hook output.

The model picker has T3's Favorites and provider rail, with Codex as the current configured provider. Stars save provider and model pairs in device preferences. Favorites survive appearance and font resets. Search hides the rail and searches the live catalog. Model and star buttons are separate grid controls, so starring does not select a model or close the picker.

## Project scripts and worktree setup

The project-file boundary ports T3 v0.0.45 `packages/contracts/src/t3ProjectFile.ts` and the JSONC reader in `packages/shared/src/schemaJson.ts`. Bot Code reads `t3.json` at the repository root without rewriting it. It accepts comments and trailing commas, trims script names and commands, and reports malformed or invalid fields visibly. Scripts retain T3's icon, `runOnWorktreeCreate`, `async`, `previewUrl`, and `autoOpenPreview` fields. Preview fields are parsed without opening a preview.

The chat header ports `ProjectScriptsControl.tsx`. Its primary button chooses the first regular script, or the first setup script when no regular script exists. The script menu lists the repository's scripts. Running a script opens a right-panel terminal tab in the current checkout. Drafts run in the repository root. The native runner starts the shell before writing the command, so attaching the terminal cannot lose the command. Scripts receive `T3CODE_PROJECT_ROOT` and worktree scripts also receive `T3CODE_WORKTREE_PATH`. The menu's **Set keyboard shortcut** records a device binding for `script.{id}.run`. IDs follow T3's name slug and collision suffix rules. The recorder refuses built-in shortcuts and duplicate script shortcuts. Script shortcuts stay inactive under Settings, Usage, and dialogs. Project config refreshes while the repository is open, and a new draft waits for it before choosing its default environment. Explicit device and project choices override `defaultThreadEnvMode`.

After Bot Code creates a worktree, a timeline card ports `chat/WorktreeSetupCard.tsx` and runs the first script marked `runOnWorktreeCreate`. It shows the command, elapsed time, and live output. A failed or interrupted attempt keeps its output and offers **Retry**. The card uses T3's neutral timeline classes and warning state. Worktree creation retains the existing branch workflow. Repositories with submodules initialize them recursively by default, at the top level with `top-level`, or leave them empty with `none`.

Setup state persists independently from Codex turns. `async` defaults to true, so setup may run while the agent works. With `async: false`, the first accepted turn waits before branch naming, checkpoint capture, and provider start until setup exits. A failed script releases that wait and retains the failed card, matching T3. A failed submodule checkout logs its failure and still runs the setup script. Per-attempt completion receipts live outside the checkout. An inherited process lock prevents retry while an earlier attempt or its descendants still run. Retry checks the receipt before rerunning a script, and a completed setup never runs again merely because the app restarted.

## Composer typing triggers and Plan

The composer ports T3 v0.0.45's plain Tiptap editor, inline file chips, `ComposerCommandMenu.tsx`, slash search ranking, `ComposerPrimaryActions.tsx`, `ProposedPlanCard.tsx`, and `proposedPlan.ts`. Ported files carry one-line source headers and retain T3's class strings. The chat column, floating composer, sidebar, header, and optional tools panel keep their existing layout.

A single trigger table owns detection. `@` starts at a token boundary and searches tracked and non-ignored untracked files in the active checkout. A repository draft searches the current checkout until its worktree exists. Selection inserts an atomic chip with the filename, file icon, and complete relative path. The canonical prompt stores T3's file-link representation, preserving paths containing spaces and punctuation through editing, clipboard, queued input, rewind, and submission. Removing or undoing a chip uses editor history. No PR `#` menu is exposed.

`$` starts a skill menu at a token boundary. Both `$pot` and `/pot` find installed skills such as `pstack:poteto-mode`. The slash menu lists skills with T3's `/skill:` prefix, description, and source badge beside the working commands. Disabled skills stay hidden, and duplicate names keep the provider's first enabled entry. Names that cannot form T3's `$name` token, including names with spaces or currency-like numeric names, stay out of the menus. Their original metadata remains intact. Skill search copies T3's `providerSkillSearch.ts` ranking over the name, display name, descriptions, and scope.

Rust parses Codex's `skills/list` response into `Skill`, retaining name, path, enabled state, scope, description, display name, and short description. Discovery uses a separate short-lived app-server with the configured Codex binary. The query cache belongs to the resolved checkout root. A new root fetches its own catalog, and reopening either menu refreshes a catalog older than 30 seconds. Every read requests `forceReload` so newly added repository skills appear. Missing, unsupported, failed, or timed-out discovery returns an empty list and leaves ordinary composition available.

Picking a skill in either menu inserts T3's atomic skill chip. Its canonical text is `$name`, preserved through copy, paste, queued input, rewind, and submission. Codex receives it inside the text input. Sent and queued user messages render known skills with T3's `SkillInlineText` and `ContextChip` components. Code and links retain literal text. Currency amounts such as `$5`, `$20k`, and `$1e6` stay prose and do not open a skill menu.

`/` starts at the beginning of a line. The menu attaches above the composer with T3's rows, selected-row shading, and descriptions. Up and Down select a result, Enter and Tab execute it, and Escape dismisses it. Empty results leave normal typing, Tab navigation, and submission available. Selection consumes only the command range and preserves surrounding prompt text. `/model` opens the existing live model picker; `/usage-limits` opens the existing usage notice. `/plan` and `/default` switch the conversation's interaction mode. The installed Codex 0.160.1 protocol has no native command-discovery method, so additional provider slash commands remain absent.

Plan controls appear only after `collaborationMode/list` advertises both Plan and Default. The compact **Build / Plan** toggle sits alongside model, effort, and access. Every turn captures those settings. Both modes send the resolved model and effort inside `turn/start.collaborationMode`, and Build explicitly clears a previous Plan mode. Providers without this capability keep the existing composer and default turns.

Only explicit Codex plan items render a proposed plan card. Its title, preview, Expand plan / Collapse plan, and Plan badge use T3's component classes. Streaming plans show Planning. A completed latest plan enables the composer follow-up actions when the turn and checkout are idle and no images, queued input, or approval are pending. Typed text becomes **Refine** and stays in Plan; an empty prompt becomes **Implement** and starts Build with T3's implementation prompt. Its dropdown offers **Implement in a new thread**, which reuses the same local checkout, worktree, or scratch folder and captures Build settings before submission. Shared worktrees keep the same branch metadata and do not receive a new generated branch name. An unavailable or busy checkout refuses creation.

Codex's `item/tool/requestUserInput` callbacks have a separate question panel, with options, permitted free text, and secret fields. Answers unblock the live callback. Open questions block ordinary sends and settings changes, signal sidebar attention, and expire when the provider stops. Historical question state and plan cards survive restart.

## Open in editor

Opening files externally ports T3 v0.0.45's `contracts/editor.ts` editor list, `shared/editor.ts` install lookup, `externalLauncher.ts` launch arguments, `OpenInPicker.tsx`, `fileContextMenu.ts`, `editorPreferences.ts` and the brand icons. Rust owns the editor table: Cursor, Trae, Kiro, VS Code, VS Code Insiders, VSCodium, Zed, Antigravity, the JetBrains IDEs and Finder. An editor counts as installed when its own launcher is an executable inside its `.app` bundle under `~/Applications` or `/Applications`, or, failing that, when its command is an executable on PATH, in `~/.local/bin`, `/opt/homebrew/bin` or `/usr/local/bin`, or among the JetBrains Toolbox scripts. T3 checks PATH first. Bot Code checks the bundle first because a PATH command can be an unrelated shim. Cursor's agent CLI installs `~/.local/bin/cursor`, which exits with an error when no IDE launcher is on PATH. A Finder-launched app finds the same editors as a terminal-launched one. Finder is always available. A JetBrains IDE found in its bundle starts through `open -na`, as JetBrains Toolbox's own scripts do, so macOS treats the IDE as its own app and not as a child of Bot Code. JetBrains counts columns from 0, so Bot Code passes one less than the link's column. A launcher that exits with an error within three seconds shows that error in a toast.

T3's Open in editor control appears in the chat header, before Git actions, for the conversation's checkout. It also appears in the file viewer's subheader, before the wrap and explorer toggles, for the open file. Its button opens the preferred editor with that editor's icon, and its chevron lists the installed editors. Picking one opens it there and makes it the preferred editor. Command+O and the palette's **Open in {editor}** open the checkout. The palette's **Reveal in Finder** selects the checkout folder. Right-clicking a diff file header or a file in a turn's changed-files card shows T3's file menu: **Open** with the default app, **Reveal in Finder**, and **Open with** with the installed editors. Right-clicking a chat file chip shows **Open in {editor}**, **Reveal in Finder**, **Copy relative path** and **Copy full path**. A chip names a file in the checkout, and clicking it still opens the right panel's file tab. A Markdown link to an absolute path outside the checkout also becomes a chip once its message is in the thread. Clicking that chip opens it in the preferred editor. Chat links that name a line, as `path:12`, `path:12:3` or `#L12`, open at that line and column. Cursor and the VS Code family receive `--goto`, the JetBrains IDEs `--line` and `--column`, and Zed `path:line:column`. The file viewer, diff headers and changed-files rows open without a line, as in T3.

General > Application has a **Preferred editor** menu. **Automatic**, the default, uses the first installed editor in T3's order. The choice saves as `preferredEditor` in `settings.json` and Restore defaults clears it. A stored editor that is no longer installed falls back to Automatic.

Rust validates every target at the IPC boundary. A workspace target is a checkout-relative path that must exist inside the conversation's checkout, outside `.git`, and must not reach outside through `..` or a symlink. The empty path names the checkout itself. A chat-link target must be an absolute existing path that a prompt, steering message, reply or plan in that thread names as a whole path. Anything else is refused with a reason in a toast. Bot Code leaves out T3's remote SSH deep links, the header's collapsed menu presentation, and other platforms' file managers.

## Editable files

The Files tab edits text files in place, as T3 v0.0.45's `FilePreviewPanel.tsx` does. `src/panel/fileSaveCoordinator.ts` and `src/panel/useFileSaveCoordinator.ts` port T3's save coordinator and its hook. An edit saves 500 ms after the last keystroke, and only the latest contents are written. An edit made during a write saves after that write. Closing the tab or opening another file saves an unsaved edit and retries a failed one. While an edit is not yet saved, the file's tab shows T3's small dot over its icon. A failed write logs a console warning, as T3's command reporter does, and keeps the dot and the edited text. The next edit, or closing the tab, retries the write.

`src/panel/fileDrafts.ts` ports T3's optimistic file overlay. Every edit stores the editor's text, and the Files tab shows that text instead of the file read from disk. Bot Code still re-reads the file after turn hints and on window focus, but the overlay hides those reads. T3 does not compare file contents to detect a conflict. So when Codex writes a file during an edit that is not yet saved, the editor keeps your text and the autosave overwrites the Codex write. After a confirmed save, Bot Code reads the file again and removes the overlay only when no newer edit exists. If that read fails, the saved contents replace the cached file and the overlay goes away, so later reads are no longer hidden. T3 keeps the overlay in that case. With no unsaved edit, a refresh loads the disk contents into the editor. Loading new contents does not write the file back.

The core's `write_file` command accepts only a path relative to the thread's checkout. It refuses `..`, absolute paths, empty segments, `.` segments, and paths inside `.git`, compared without letter case. It also refuses a path that continues below a file. It also refuses a symlink that resolves outside the checkout or into `.git`, a dangling symlink, a folder, and contents over the 1 MB text limit. The checks run before any change on disk. The command creates missing parent folders and writes the file in place, which keeps its permissions. It takes no checkout hold, because an in-app save behaves like a save from another editor. In T3, only host files outside the workspace open read-only. Bot Code opens only files listed in the checkout and refuses a symlink that leads outside it, so every file the tab can show is inside the workspace. Binary, non-UTF-8, and oversized files keep their read-only notice. Bot Code leaves out T3's line review comments, rendered Markdown, table and HTML views, and the editor's undo history across tab switches.

## Domain data the interface needs

T3's timeline reads timestamps that Bot Code did not record before this baseline. Each `Turn` now stores `started_at` and `completed_at` in Unix milliseconds. `ThreadSnapshot::stamp_completions` records completion on every save. Turns saved earlier have neither value and show "Worked" instead of "Worked for 8.6s". `ThreadSummary` carries `updated_at` for the sidebar's relative time, `awaiting_approval` for its **Approval** status, and `pinned_at_ms`, `snoozed_until_ms`, and `settled_at_ms` for the sidebar sections. It derives `archived_at_ms` and `created_at_ms` for Archived settings. Each thread stores a `placement` of `auto`, `kept`, `pinned`, `settled`, or `archived`, and an optional `snooze` with its wake time and the time it was set. An `archived` placement carries its timestamp and a `LivePlacement` restore value that excludes archive, so archives cannot nest. A `pinned` placement carries `kept`, T3's active override, when pinning un-settled the thread. Pins saved without `kept` load with it false. Snapshots saved with the earlier `settlement` field load it as `placement`. The core reports the wake time only while no approval or newer turn result cancels the snooze. The client compares that time with its own clock. The effective settled time is derived when it is read. The core reads `sidebarAutoSettleAfterDays` and each `projectOverrides` entry from `settings.json` when it opens and after every settings save. A missing or invalid value means 3 days, and `null` turns auto-settling off. A save that changes a thread's classification sends a change hint for that thread. Before a pin, settle, snooze, prompt or approval changes a thread, the core stores a due auto-settle as `settled` at the last activity, without the pin or the snooze, as T3's auto-settle command does. `pinned_at_ms` is empty while a pinned thread reads as settled. File-change items carry their `paths`, so a single change shows its file name. Each Codex item kind has its own turn item, such as `reasoning`, `mcp_tool_call`, `web_search`, and `context_compaction`, with the fields its row needs. Snapshots saved with the earlier `other` items load them as reasoning or context compaction and drop the rest, which carried no text. Each thread stores its latest `context` usage from Codex: the tokens in the context window, the window's size and the total processed. Threads saved earlier have none and show no meter.

A collapsible Checks section, closed by default, lists every check and offers Fix check on failed or cancelled ones. The **…** menu holds **All pull requests**, which returns to the list, Refresh, Explain with Codex, Fix findings, every permitted lifecycle action that the header does not already show, and Open on GitHub. Timeline combines opened, commits, comments, reviews, and merged or closed events in newest-first order. Dates that GitHub omits or returns invalid remain unavailable. Code renders the remote pull request files with the pierre diff, as T3's Code tab does. Its toolbar shows the file count on the left. ## PR lifecycle

Saved PR detail exposes working lifecycle controls from GitHub permissions and repository policy. The primary action follows the observed state. It offers Resolve conflicts, Ready for review, an allowed merge method, required merge queue or auto-merge in the header, using T3's labels such as **Squash and merge** and **Auto-merge (squash and merge)**. Armed auto-merge shows T3's blue badge with its method, and a queued, merged or closed pull request shows a badge in the same place. The **…** menu includes supported draft, ready, close, reopen, branch update and auto-merge controls. Conflicts keep permitted auto-merge available as a secondary action. GitHub's required queue chooses its merge method.

Every lifecycle mutation opens a confirmation with the captured PR identity, head and account. Auto-merge warns that GitHub may merge immediately. A changed head or account refuses the captured request. Checkout-changing actions also refuse while a linked conversation uses that checkout. Disable auto-merge remains available during agent work.

Accepted queue, armed auto-merge and unavailable confirmation reads stay pending. The conversation stays active until a fresh host observation confirms the outcome. Reconcile reads GitHub without replaying the original mutation. Pending receipts and links survive restart.

An interrupted branch update keeps its outcome unknown. When the same PR is open at another head, Continue from inspected head shows the original method, head and account beside the current head and account. Its explicit confirmation warns that GitHub may still apply the earlier update and continuation does not cancel it. Successful continuation saves the inspected identity while preserving the original request. A fresh same-node merged observation also clears obsolete lifecycle blockers without claiming the earlier uncertain operation succeeded.

Resolve conflicts and Fix findings append captured identity, current unresolved findings, failed checks and coverage warnings to the conversation draft. They include startup failures. They preserve existing text and require the user to Send.

General settings adds Auto-settle merged pull requests independently from Auto-settle inactive threads. Its project override, inheritance indicator and reset follow the existing settings structure. Eligible conversations settle after all linked PRs merge and a merge is recent enough for their trusted activity. New work, kept placement, snooze, approvals and running work protect active conversations. The settled age remains the conversation's activity age.
