# First-slice architecture

The selected design uses one Rust runtime owner and one lazily started Codex app-server. The Tauri adapter validates IPC values through serde and forwards the core's public operations. The React renderer uses TanStack Query snapshots and committed invalidation hints. TanStack Router owns the selected repository and conversation. The right panel keeps its open tabs in component state for the current repository.

## Ownership

`runtime.rs` owns conversation transitions, canonical checkout leases, approval callback routes, and the single SQLite writer. Its loop processes commands, provider notifications, asynchronous request completions, and a streaming commit timer. Provider requests run outside that loop. The private Codex transport owns its request-correlation map and serialized JSONL writes.

`store.rs` stores workspaces, thread snapshots, and operation receipts. WAL and short transactions preserve the local intent and receipt together. A file lock excludes a second runtime using the same state directory. The snapshot format replaces the proposed normalized item tables for this bounded slice. Machine-local renderer UI state, such as panel widths, lives in the `ui_state` key-value table instead of WebView storage. Preferences live in `settings.json` in the data directory, so a user can edit or sync them. Saves write to the resolved symlink target through a temporary file and a rename.

`repo.rs` validates Git roots and canonical path containment. It excludes `.git` reads and external symlinks. File and historical blob reads have a 1 MB text limit. Git arguments do not pass through a shell. Git runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, and `LC_ALL=C`, so a credential prompt fails instead of waiting, and error text is English for matching. Repository inspection runs outside the conversation owner. Refresh is explicit, on focus, and after turn completion.

`codex.rs` starts the installed binary, initializes app-server, correlates responses, and forwards notifications and reverse requests. Transport framing and writes are bounded. The child uses a separate Unix process group. One task owns the child and publishes its exit status, so a crash is detected even when a descendant keeps stdout open. After the exit, the reader drains stdout for up to 500 ms. Shutdown signals the group, waits for that status, and kills remaining group members. Dropping the last handle kills the group. Unsupported reverse requests receive an explicit protocol error. Each stderr line goes to `<data dir>/logs/codex.log` through `log.rs`, which rotates at 1 MiB and keeps three older files. The transport also keeps the last 40 lines, each cut to 300 characters. Logging failures never reach the caller.

## Usage history

`usage_history.rs` owns transcript history separately from the live provider actor. It scans `sessions` and `archived_sessions` under `CODEX_HOME`, or `~/.codex` when it is unset, including sessions outside Bot Code. Its parser normalizes token categories and suppresses duplicate events and copied fork prefixes. Processed tokens count uncached input, cached input, cache creation, and output once. Reasoning is a subset of output.

A serialized blocking worker reads history without blocking conversation transitions. The bounded `usage-scan-cache.json` in the app data directory reuses unchanged files and retains records from removed or incompletely read sources for 90 days, with partial-coverage warnings. Reports aggregate a rolling 24-hour window or 7, 30, or 90 local calendar days by time and model.

`usage_history/pricing.rs` caches LiteLLM's published base rates in `usage-model-rates.json`, with the source, fetch time, and content fingerprint. Estimates describe API-equivalent USD costs. Unknown models remain in token totals and unpriced coverage. Stale cached rates remain usable when a fetch fails. The renderer stores metric, period, and breakdown preferences in the native `ui_state` table, scoped to the app data directory.

## Agent tools

`tools.rs` defines provider-neutral specifications, calls, invocation context, and text or image results. Its registry combines the three PR-link tools with an optional preview backend. `runtime/tools.rs` dispatches PR operations through the existing owner and runs preview futures outside its loop. It validates the live native thread and turn before dispatch and again before completion. Eight preview calls may run at once. Provider loss and interruption cancel pending work without replay.

The desktop uses `App::open_with_tools` with stdio registration. The same executable starts in `--agent-tools` mode before any Tauri window or database opens. `tool_bridge.rs` forwards bounded MCP JSONL calls through a private mode-0600 Unix socket in a mode-0700 temporary directory. A random credential binds each bridge to one local conversation and provider epoch. Credentials stay in the MCP process environment. Restart revokes them. Codex start, resume, and fork config names only the registered tools as approved application tools.

`codex/tools.rs` isolates provider metadata, dynamic declarations, MCP configuration, and result encoding. Core-only callers use dynamic registration and `item/tool/call` replies through the same registry. Dynamic declarations persist across Codex restart, but Codex 0.160.1 cannot add them on resume. Stored catalog fingerprints prevent guidance from advertising unregistered dynamic tools. Desktop MCP registration can add tools to existing native conversations.

Tool guidance goes in the per-turn `additionalContext` application entry. PR-only sessions receive only the PR sentence. The preview paragraph appears only when that backend registers its tools. Schemas and descriptions carry the operation details. [Preview design](preview-design.md) records the alternatives and native prototypes; [verification](preview-verification.md) records delivery checks and token measurements.

## Native preview

`src-tauri/src/preview` adapts T3's preview manager and port scanner to a Tauri 2 child webview. Its model separates thread and draft scopes, browser state, requested CSS viewport, native geometry, navigation generation, and one active geometry lease. A monotonically increasing lease and sequence reject late layout and detach calls. The manager retains a bounded cache of private browser views and evicts hidden scopes. Fixed viewports use native zoom and proportional geometry; hidden views retain their own CSS size. The native adapter measures `innerWidth` and `innerHeight` after layout.

`src/preview` ports T3's browser chrome, empty and discovery states, and device toolbar. React owns Preview tab intent, subscribes to scoped state events, and measures the host. Attachment acquisition is serialized across mounts; disposed mounts cannot acquire after a newer owner. Resize and mutation observers hide the native sibling view for inactive content and application overlays. Coalesced microtasks apply geometry because WKWebView can pause animation frames and report the main document hidden while its native window remains visible. The parent window controls OS hiding and minimization. A navigation requests panel opening once; later readiness or load results only update state. Script completion captures its original scope before applying `previewUrl` and `autoOpenPreview`.

Native page load and requested-navigation supervision have bounded lifetimes. An active-lease poll observes same-document SPA URL and history changes. Loaded pages reload through the native browser; failed or missing pages retry the requested URL. Local discovery reads listeners and probes only loopback HTTP servers, with request, output and concurrency limits.

The preview backend registers twelve provider-neutral tools. Typed arguments reject conversation identities, invalid URLs, unsupported resize combinations, and oversized inputs at the adapter boundary. Each browser has a private snapshot namespace and operation mutex. In-flight calls pin its cache entry; waits release the mutex between polls. Cancellation settles only its pending navigation generation. A 65-second execution deadline leaves room for the 60-second wait tool; the bridge and MCP deadlines are 70 and 75 seconds.

DOM automation evaluates one synchronous function in the main frame. Snapshot references expire on a new snapshot, replacement, or navigation. Semantic results omit password values and bound text and element counts. Evaluation expressions and values are limited to 64 KiB; promises, cycles, and BigInt are refused. The native adapter waits for the view's first committed navigation before dispatching any evaluation, avoiding Wry's pre-commit script queue. It serializes results to primitive JSON strings in JavaScript before native serialization and bounds both decoded and escaped envelopes. macOS captures PNGs through WKWebView and applies NSAppearance. A 4.4 MB PNG cap fits the 6 MB tool-result and 8 MB provider-frame limits. Optional saves use generated filenames inside the isolated app data directory.

External views have no application capabilities. The capability file names only the main webview, and the custom command handler independently rejects every other view. Tauri adds every plugin's initialization script to every webview, so the dialog and notification plugins are wrapped in `MainViewOnly`, which runs their scripts only when the view's label is `main`. Before, a child page's `alert`, `confirm` and `Notification` were IPC calls that the capabilities refused, and noVNC reported the rejected permission check as an error. The attachment URI handler also checks the main view identity. Application events target the main view. Navigation accepts HTTP and HTTPS, denies new native windows and downloads, and redirects requested browser popups into their own scoped view. Preview uses private browsing and imports no cookies.

The Desktop tab reuses this host with a third scope, `desktop` with a thread id, which agent tools never address. `preview_close` closes a scope's view and forgets its state. The tab opens its view when it mounts and closes it when it unmounts, so a hidden tab, a closed panel or another thread ends the stream instead of leaving a hidden page connected. The desktop page carries `<meta name="botcode-discovery" content="none">`, and local server discovery skips any page with that tag, so a sandbox's published port does not appear among Preview's local servers.

On macOS, a local AppKit event monitor relays registered application chords from the visible child webview to the existing action registry. Main-window, first-responder, and preview-scope checks prevent other windows or stale queued events from invoking an action. It exposes no page IPC and requests no OS input permission.

## Checkouts

Each thread records a `Checkout`. A local thread runs in the repository's own checkout. A worktree thread runs in a Git worktree on a fresh `botcode/<id>` branch, under `<data dir>/worktrees/<repository>/botcode-<id>`. The draft's `NewCheckout` names the base branch. With `fromOrigin` and an `origin` remote, the runtime fetches the base from origin and starts from `origin/<base>` when it exists, else from the local base. A failed fetch fails the creation. The branch is created with `--no-track`, so a user's `branch.autoSetupMerge` cannot make it track the base, and its base is recorded as `branch.<branch>.gh-merge-base`. Git actions read that key as the pull request base, and `gh` reads it too. The renderer sets `fromOrigin` only when origin has remote-tracking refs and the base is a local branch, which is when the picker reads "From origin/{base}". The runtime creates the worktree outside the owner loop when the thread is created, which happens on the first send. A repository without commits cannot start one.

`ThreadSnapshot::root` resolves the directory a thread runs in. The Codex `cwd`, the checkout lease, and the workspace view, file and diff reads all go through it. Leases are keyed by that root, so a worktree thread never waits on the local checkout or another worktree. Two local threads still exclude each other. `switch_branch` changes the branch of the checkout a thread resolves to. The owner rejects it with `checkout_busy` while that checkout's lease is held, and rejects submits there until it finishes. A worktree thread's stored branch follows the switch. The renderer scopes workspace, file, diff and branch queries by `CheckoutRef`. Local threads share the repository-scoped cache entry. `cleanup.rs` removes eligible worktrees when optional thread-deletion cleanup or inactive or unchanged worktree rules apply. Cleanup checks checkout holds and local state before removal. Automatic cleanup retains the thread and branch, so the next message can recreate its worktree.

## Git actions

`vcs.rs` owns the Git actions. It reads a checkout's status, looks up its pull request with `gh`, plans an action, and runs it. Every git and `gh` call goes through `vcs::Tool`, an async runner with no shell, stdin closed, the non-interactive environment, and a time limit. Local commands get 30 seconds, `git commit` gets 10 minutes for hooks, and the `gh` lookup gets 15 seconds. Push, pull, and `gh pr create` get `RuntimeConfig::network_timeout`, 180 seconds by default. Each tool runs in its own process group. On timeout the runner sends SIGTERM to the group, so git can remove its lockfiles, and SIGKILL to whatever remains 2 seconds later. `RuntimeConfig::gh_binary` comes from `BOT_CODE_GH_BIN`, then `PATH`, `~/.local/bin`, `/opt/homebrew/bin`, and `/usr/local/bin`, because an app opened from Finder has a minimal `PATH`. Codex resolves the same way.

`App::git_status` reads porcelain v2 status, numstat against HEAD, `origin`, and the branch's config. It never touches the network. A branch has an upstream only when it tracks a remote branch of the same name. A branch that tracks a differently named branch was cut from it, so that branch is its base and not a push target. The base is `gh-merge-base`, else that tracked branch, else the default branch. `ahead_of_base` counts the commits on HEAD that `origin/<base>` lacks. `App::pull_request` runs `gh pr list --head <branch>` and returns a missing, signed-out, or failing `gh` as data, so the header renders without it.

`App::run_git_action` claims the checkout with `Hold::Git` through the owner's `Claim` and `Release` commands, which `switch_branch` uses with `Hold::Switch`. A claim refuses while a turn holds the lease, with "Codex is working in this checkout", and while any other hold is set. Submits, switches, worktree cleanup, and project removal already check for a hold, so a Git action excludes them too. The action body runs in a spawned task, so the hold is released even when the caller drops its future. A second spawned task keeps a panic in a step from skipping the release.


`App::publish_repository` uses the same owner-managed Git job and checkout hold for GitHub creation, remote configuration and push. `vcs/publish.rs` validates repository and remote names, captures the branch and optional commit, and pins readiness and creation to GitHub.com. It compares every configured fetch and push URL before reusing a remote, otherwise adds a free name without replacing another remote. After creation and remote setup it rechecks the captured checkout; a changed or unreadable branch or commit returns the known remote-added stage without pushing. An unchanged branch pushes a full named source and destination ref and sets its upstream. An unborn checkout completes after remote configuration.

Publication outcomes distinguish success, a failure with its last completed stage, and uncertain repository creation. Bounded Git errors retain their actionable cause, while GitHub denials use specific safe guidance without exposing authentication output. Known creation and remote effects are never rolled back or silently recreated. An ambiguous creation response requires checking GitHub before retrying. External Git is not serialized; it can still move the named branch between final inspection and push. The renderer wizard captures its checkout identity, ignores stale completion, locks dismissal while pending and refreshes the existing query scopes on completion.

`vcs::plan` is a pure function from the action, status and pull request lookup to the steps. Ordinary stacks resolve publication targets before staging or generation. The steps run in order: prepare the selected index and message, commit, push, then generate pull request text and run `gh pr create --title <title> --body-file <private file> --base <base> --head <branch>`. A branch without an upstream pushes with `-u` to `origin`. Before that push, the plan records the base in `gh-merge-base`, because the new upstream replaces the tracked branch the base came from. An open pull request for the branch is returned instead of a new one. `Err` means the action never started. `Ok(GitOutcome)` reports every step that landed and the step that failed. Progress goes to the renderer over a per-call Tauri `Channel<GitPhase>`.

`Plan::FeatureStack` captures the original base and requested commit with a typed Push or PushPr tail. Under the same `Hold::Git`, it prepares the selected index and resolved message once, checks out a collision-safe branch with `--no-track`, records the observed branch and original base, then rereads status and checks publication targets for the new head. `CommitStep::Prepared` tells PR eligibility that a commit will consume the selected index even when excluded files remain dirty. These checks run before the commit. Preparation failures can retain the new branch and staged index; the Branch phase and outcome report that state. Existing owner completion updates managed-worktree branch metadata even after a later failure.

Holds live in memory, so a crash leaves none behind. Commit refuses an empty index, push runs only when the branch is ahead, and the pull request step finds an open pull request. A feature-branch preparation can leave a branch or staged files before a failure; it does not roll them back or promise that repeating branch creation converges. A killed Git process can also leave `.git/index.lock`. Git reports it, and Bot Code does not delete it.

`text_generation.rs` extracts the existing worktree naming runner into one shared Codex exec path. Naming and Git writing use the captured thread model through `Owner::resolve_model`, ephemeral read-only execution in a disposable directory, low reasoning effort, JSON output schemas, bounded stdin and output, and the existing cancellable `vcs::Tool` process-group runner. The prompts port T3 v0.0.45's commit and pull request rules. Patch sections truncate at 40,000 bytes with an explicit marker after a bounded Git read. `settings.rs` projects the persisted source-control settings into a resolved project writing policy. Commit previews and actions capture that policy before spawning. Repository conventions add recent non-merge subjects and bounded root `AGENTS.md` guidance; conventional and custom modes port T3's prompts. PR template detection reads supported files from the captured base tree, rejects ambiguous directories and bounds template content. The renderer applies the project merge default between the current PR choice and last-selected history.

`runtime/source_control.rs` keeps startup admission and fetch deadlines for canonical existing repository and managed-worktree checkout paths. The Owner bounds jobs to four and serializes linked checkouts within a project because they share refs. `Hold::SourceControl` uses existing checkout exclusion while preserving background naming; pending commit previews defer admission. Interval zero disables periodic fetch, while an enabled startup auto-pull can fetch a cached-behind default checkout. `vcs::automatic_refresh` requires known `origin/HEAD`, clean state, a same-name upstream, no local commits and no operation sentinel, then rechecks branch and status before a fast-forward. Completion releases the hold and refreshes workspace hints and affected PR discovery. Shutdown cancels and drains jobs.

Commit actions carry an optional validated `CommitMessage`. `Plan::Stack::commit` holds a `CommitStep`, either Requested with a `CommitRequest` or Prepared with its resolved message. Both represent a planned commit. Ordinary preflight runs before generation; feature stacks prepare once before resolving targets on the new branch. All-selected preparation uses `git add -A`; a subset clears the index and stages literal selected paths. A typed message bypasses generation. A blank message generates from `git diff --cached` and its stat. Invalid output, timeout, or provider failure reports a commit failure that asks for a typed message, without committing or starting later steps.

The PR step generates after the planned commit and push, using the recorded base. It resolves `refs/remotes/origin/<base>` before `refs/heads/<base>`, matching the ahead-of-base check, and captures base and HEAD commit IDs for the context reads. Its commit log uses base..HEAD and its diff uses base...HEAD. Generated Markdown goes through a private temporary body file. Existing PRs bypass generation. Invalid output or generation failure falls back to `gh pr create --fill`, and `GitOutcome::warnings` retains that note whether PR creation succeeds or fails.

`runtime/writing.rs` owns commit preview jobs without a mutation lease. The begin operation acknowledges an owner-generated job ID before the renderer awaits its result, so closing during registration still cancels the eventual job. At most four workers are admitted. Unclaimed results expire after 150 seconds. A preview copies the checkout-specific index beside the real index, removes split-index dependencies on that copy, stages all changes into the private copy, and generates from its cached diff. An unborn checkout starts with an empty private index. The real index remains unchanged. Cancel, submit, thread change, foreground checkout claims, worktree cleanup, successful project removal, provider loss, and shutdown cancel previews through the same process-group cleanup. Project removal cancels only the removed threads' previews. Cancelling does not wait for the worker to finish, so manual submission and plan preflight remain responsive. The owner drains workers on shutdown.

The dialog preserves edits made during generation. A visible generated message is treated as the user's approved text on submission, while a blank submission cancels the preview and generates again from the actual staged diff. Commit-generation failure offers a **Commit** action that reopens the editable dialog.

The renderer keeps local status under the `git` query scope and the pull request under `pr`, keyed by branch with a 60-second stale time. Window focus refreshes every scope except `pr`, because `pr` runs `gh` over the network. Turn completion refreshes `git`. Opening the menu and finishing an action refresh both. The quick action and menu rules are T3's, ported to `GitActionsControl.logic.ts` with T3's own test. Bot Code's policy in `gitActions.ts` adds the `gh` and Codex states, the order of the commit and default-branch dialogs, and the result toast. A typed continuation retains the approved request for current-branch or feature-branch execution. Feature choice keeps clean commit stacks intact for the exact native no-changes refusal. Direct noncommit feature choices refuse at the renderer boundary before native dispatch. Result actions use a reported new branch instead of pre-action default-branch or PR facts. `pnpm test:ui` runs both with `node --test`.

## PR review triage

`pr_review.rs` defines observation-bound review data and actions. `pr_review/host.rs` reads the saved PR through explicit repository and PR identities. Every host call pins `github.com`. Review threads, conversation comments, reviews, checks, files, and commits load independently. A failed or limited section contributes one typed `PrSectionProblem`, while successful sections remain available. Initial and final core metadata must agree on PR identity, head, and viewer. Identity changes, cancellation, and process cleanup failures abort the detail read.

`ReviewFinding` keeps immutable PR and finding IDs, the observed head, and a digest of the original source and comments. Comments retain source URLs, author, timestamps, and original commit, path, line, and hunk. Timeline entries combine opened, commit, comment, review, and merged or closed events in newest-first order. Merge takes precedence over close. Invalid dates remain unavailable and sort after dated events.

The existing runtime Owner admits at most four review jobs, coalesces detail reads by PR, and owns all SQLite writes. Failed core reads retain the canonical snapshot, persist stale freshness, and notify every linked conversation. Successful final metadata refreshes that shared record even when an optional section failed. Local triage uses saved PR membership and the exact observed finding, without requiring its checkout branch. `review_dispositions` retains its per-workspace keys and compare-and-set behavior.

Host reads bound each process to 2 MiB and 15 seconds, the full detail to 16 MiB and 32 calls, and each connection to four pages. The overall timeout is at most 90 seconds. Optional sections reserve 2 MiB, final-call capacity, and up to 15 seconds for core confirmation. Child processes are terminated and reaped on cancellation. The owner drains admitted mutations and persists their receipts before shutdown acknowledgment.

Review, reply, and resolution commands revalidate the target and host permissions. Review line anchors must belong to the current remote diff. Mutation bodies use a private mode-0600 JSON file and never appear in process arguments. Exact-input receipts prevent automatic duplicate submission after restart. Known pre-dispatch denials return refused. Dispatched ambiguity or failed completion persistence remains uncertain.

The optional Pull requests panel offers Summary, Timeline, and remote Code after branch switches or worktree removal. Missing or truncated patches expose no inline anchors. Revisioned session drafts belong to PR, viewer, and head, preserving edits made during submission. A returned review ID clears only unchanged captured revisions. Ask, Explain, Fix finding, and Fix check append original evidence and bounded typed coverage warnings to the captured conversation draft, focus its composer, and require explicit Send.

## Turn checkpoints and rewind

`checkpoints.rs` ports the hidden-ref capture, diff, and restore behavior from T3 Code v0.0.45's `CheckpointStore.ts`, `CheckpointDiffQuery.ts`, and `GitVcsDriver.ts`. Each turn has an immutable before and after commit under `refs/botcode/checkpoints/<thread>/<turn>/<boundary>`. The refs live in the repository's common Git directory, so linked worktrees share the object store and worktree removal does not erase history. Checkpoint commits have no branch parent. They never move HEAD or appear in the current branch's log.

Capture copies the checkout's real Git index into a private temporary index. It stages the working-tree contents there and explicitly rehashes the indexed paths, then writes a tree and commit, and publishes the boundary ref only if it is absent. A retry adopts the existing ref. The real index, HEAD, and branch remain unchanged. This includes tracked files, even when an ignore rule matches them, and non-ignored untracked files. Ignored untracked files are excluded. File modes, binary contents, and symlinks belong to Git's tree. Nested repositories and submodule contents have no recursive snapshot coverage.

`Turn` records the prompt, ordered image attachments, native turn identity, delivery and execution states, items, settings, timestamps, and checkpoint. `Turn.checkpoint` describes Pending, Before, Complete, or Unavailable. Each checkpoint stores its ref name and immutable commit ID. Before stores the checkpoint captured before dispatch. Complete adds the after checkpoint and changed-file stats. Unavailable retains a before checkpoint when one exists and records the reason. Old saved turns default to Unavailable and never substitute the current checkout for a historical diff. Renames appear as a deletion and an addition. Binary file stats have null line counts. Historical text reads allow UTF-8 blobs up to 1 MB. Checkpoint queries bound Git output to 16 MB, file lists to 40,000 entries, and individual Git processes and pipe collection to 60 seconds.

The runtime owner accepts the local turn and takes the canonical checkout lease before starting capture. A repository capture must persist before `turn/start` is dispatched. Capture failure leaves the turn NotSent. A turn keeps its checkout excluded through final capture and snapshot persistence. Provider loss cannot release an in-flight checkpoint worker's separate hold. File diffs read the two saved commits, including through the parent repository after a worktree has been removed. The storage sweep retains hidden refs while it retains thread history, and refuses active capture or pending rewind. Project removal leaves repository refs on disk. Automatic reclamation of orphan checkpoint refs is deferred.

Both rewind choices remove the selected turn and every later local turn. Revert and keep changes leaves the checkout untouched. Revert files too restores the selected turn's before checkpoint without moving HEAD or the branch. As in T3, it restores the index and working tree, removes later non-ignored files, then resets the index to HEAD when HEAD exists. Restored changes therefore appear unstaged. An unborn repository has no HEAD to reset to. Ignored files remain outside coverage. Restore refuses ignored path collisions, unsafe nested repositories or submodules, and ignore-rule changes while ignored files need preservation, before destructive writes.

The installed Codex 0.160.1 app-server has no `thread/rollback`. Its `thread/revert` works only for paginated native history, and a repeated successful request fails because the target turn is gone. Legacy native threads reject it. Bot Code uses the verified `thread/fork` operation with `beforeTurnId` for a retained prefix instead. The Bot Code conversation ID and checkout stay the same, and its native Codex thread ID changes. The original native history remains intact. A rewind to an empty prefix starts a fresh native thread on the next send. The dialog explicitly describes the new native thread, so a local timeline edit never implies that Codex forgot context it still holds.

`ThreadSnapshot.pendingRevert` stores the caller request ID, target turn, file mode, fixed source native identity, expected retained native turn IDs, checkpoint, checkout root, and recovery phase. Preparing precedes the fork; ConversationReady persists the verified prefix fork; RestoringFiles precedes filesystem writes; FilesRestored records successful restoration. The owner persists the intent under `Hold::Revert` before provider or file work. The final SQLite transaction replaces native identity, truncates turns and approvals, clears context usage, saves `lastRevert` with the original prompt, ordered image attachment metadata, and retained turn count, clears the intent, and writes the exact-input operation receipt together.

Startup reconstructs pending checkout holds. Retry uses the saved request and target. Preflight refusal clears the intent and releases the hold after that clearing is durable, allowing another mode or a new turn. Failures after a fork or file work retain the intent and expose Retry revert. Preparing can create another prefix fork from the unchanged source; a lost fork response can leave an unused native thread. The owner caches completed captures and restorations while their saves retry, retaining checkout exclusion. FilesRestored retries only final persistence. A completed receipt is checked before target lookup and never restores files again, even after later edits. A conflicting request ID refuses. These are application checkout holds; they do not lock out external editors or terminals. Filesystem work and SQLite cannot commit atomically, so a crash before FilesRestored becomes durable may repeat restoration to the fixed checkpoint.

Removing a worktree preserves historical diffs through the common repository. File rewind requires the checkout to exist and refuses before recording an intent when it is missing. Conversation-only rewind can fork with the repository root as cwd, and the next send uses the existing worktree restoration path. Sparse checkouts, submodules, nested repositories at restore targets, directory symlinks, and ignored-file collisions are refused. Collision checks use filesystem identity as well as path spelling to protect case and Unicode aliases on macOS. No sweep currently deletes checkpoint refs, including refs for removed timeline turns; automatic orphan reclamation remains deferred.

The React timeline ports T3's ChangedFilesTree and Edit from here button. The Diff panel's existing Git scopes remain available beside Latest turn and Turn. Historical queries use thread and turn identities, and switching threads or removing a selected turn invalidates that selection. Successful rewind merges the prompt and images with the current unsent input without sending it. One local composer value accepts text, images, and the applied request ID together. Staging or the 100-image limit defers the entire merge with guidance; removals or completed staging retry it. Initial rewind uses the same fit check, but a saved pending rewind always remains retryable. Revision-guarded snapshots are the sole recovery source, and activation and edit-generation guards keep late staging and send callbacks from changing another draft.

## Durable conversation behavior

A submit carries a caller operation ID. The owner validates the prompt and checkout lease, then commits the local turn and receipt together. Reusing the same ID and input returns the original turn. Reusing the ID for different input fails.

The same submit IPC accepts an optional exact local `expectedTurnId` for steering. `App::submit_to` adapts that intent to the owner without changing ordinary `App::submit` or its receipt serialization. Both paths share prompt and attachment validation and `Store::accept`. A steer requires the current accepted Running turn, its native identities, the existing checkout lease, no approval or revert, and no unresolved steering input. The receipt points to the parent turn. `Item::UserInput` holds its own operation ID, text, images, and delivery state inside that turn. Steering creates no turn, checkpoint, or lease.

The owner saves Preparing with the receipt, then saves Sending through clone-save-install before `turn/steer` can write to the provider. The wire request carries the exact native turn ID and caller user-message ID. A matching RPC acknowledgment, or a `userMessage` with the matching client ID inside the expected native turn, confirms acceptance. Live started/completed events and full native history reconcile every steering item. Native item IDs do not replace caller IDs. Parent completion alone provides no steering delivery evidence. An explicit provider rejection becomes NotSent. Transport loss or a mismatched acknowledgment becomes Uncertain and retires execution. Positive user-message evidence survives stale errors. Startup and provider loss classify every Preparing or Sending item without replay, even if its parent already ended. Attachment cleanup counts steering images in archived history. Turn rewind truncates all steering items with their parent, keeps operation receipts, and recovers only original input.

`chat/followUps.ts` owns renderer intent in memory, with one FIFO per thread and waiting, preparing, dispatching, held, and checking states. Each immutable input captures staged attachments and send settings. A synchronous claim prevents repeat effects and manual clicks from dispatching twice. `FollowUpSender` mounts above the router and observes authoritative queries for hidden queues through the existing batched invalidations. Automatic dispatch needs a visible, accepted, successfully completed predecessor, closed checkpoints, and no approval, revert, or failed or uncertain steer. A receipt removes its row and establishes a barrier until that accepted turn appears and completes. Stale Ready snapshots cannot advance another row. Reusing an empty queue starts from its current ordinary turn.

Send now fixes its start or exact-turn steering intent before IPC. Retries preserve that intent and operation ID. Ambiguous renderer responses hold the row in checking until explicit Check delivery retries the same receipt. Later messages stay held. Settings preparation and receipt callbacks require the captured claim identity. Stop or Remove can cancel before dispatch, and stale callbacks cannot change a later retry of that row. Stop synchronously holds the queue before interrupt and merges recoverable input with the active draft. Image staging or capacity retains held rows. Dispatching and checking input cannot be restored as unsent. Rewind holds the queue, and archive, deletion, and project removal refuse renderer queues until the user removes their rows. Switching threads preserves queues. Renderer reload and app exit intentionally discard waiting intent, as T3 does. Durable accepted history remains.

Preparing, Sending, Accepted, NotSent, and Uncertain are distinct delivery states. Execution has separate NotStarted, Running, Completed, Interrupted, Failed, and Lost states. The native thread ID commits before a turn is dispatched. Native started/completed notifications can establish acceptance even if the start response is lost. A stale response error cannot undo confirmed completion or stop a newer turn.

Streaming updates accumulate in the owner and commit about every 90 milliseconds. A queried snapshot flushes pending changes before returning. Completed native items replace accumulated partial content by item ID. Commit precedes every invalidation hint. The renderer batches thread invalidations and refreshes authoritative snapshots instead of replaying a frontend event log. Every query-cache write preserves a newer revision. Terminal hints refresh their workspace and file/diff queries even when that conversation is hidden; streamed tokens do not repeatedly run Git inspection.

Approval callbacks map an application approval ID to the reverse JSON-RPC request ID, provider epoch, and item ID. Missing action details prevent acceptance. Later file-change items can supply those details. Clone-save-install transitions preserve the pending callback and running state when an approval or interruption save fails. Repeated approval clicks cannot send the callback twice.

`runtime/providers.rs` keeps one app-server slot per execution environment. The thread's checkout derives its `EnvKey`, `Mac` or `Sandbox(id)`, so threads that share a sandbox share its agent. A slot is Idle, Launching or Live, and the type allows no other combination. Epochs come from one counter shared by every slot, so an epoch names one process generation of one slot. A signal, completion, callback route or tool scope whose epoch no slot holds is dropped. An agent can address only the threads of its own environment. Approvals, questions, notifications, subagent events and dynamic tool calls look up the native thread among that environment's threads, and a tool call must also come from the slot of its target thread. The model list, collaboration modes and usage limits come from the Mac agent, and rate-limit updates from other agents are ignored. While the Mac agent has not run, the first sandbox agent's model list stands in, because the image pins the host Codex version, so a sandbox turn can name its model and collaboration mode. `Launcher` is the one place an agent starts. The Mac arm runs `codex app-server` as before. The sandbox arm reads the Mac's Codex credentials first, so a signed-out Mac fails with "Sign in to Codex on this Mac first." before any Docker work, then readies the container, starts the in-image `agent` script over `docker exec`, initializes, signs the agent in with `account/login/start`, and discovers its modes.

On provider loss, the runtime terminates that slot's process, retires its epoch, expires its threads' callbacks, marks their unresolved turns Lost or Uncertain, and releases their checkout leases. Threads of other environments keep their turns, callbacks and leases. Shutdown and a failed progress save lose every slot. It does not replay turn/start. Startup restores local history and marks previously live execution unresolved. Reconnect resumes the exact native thread and merges matching native turn or client-message identities when returned. Incomplete history never deletes local items or proves lost execution live.

A process exit becomes `codex::Exit`, with the exit status, an optional transport cause, and the stderr tail. Its headline names the signal or exit code and goes to the session and to the banner of each thread that lost work: an active turn, an open approval or question, or an unconfirmed steering input. Idle threads become Unavailable without a banner and resume on next use. The headline and the last 12 stderr lines go on each lost turn and its unsent or uncertain delivery. A second loss reports only unsettled work, so it never rewrites a turn an earlier crash settled. Pending RPCs fail with the same text. A completion that failed this way returns without action, because the process's `Exited` signal follows it. A write that fails after Codex exited reports the same code, so a request sent in the moment after a kill does not record a generic error. So a crash during `initialize`, `turn/start`, `turn/steer`, or `turn/interrupt` reports the exit and stderr instead of a generic delivery error. A launch still sleeping out its backoff when Bot Code closes never starts Codex. The timeline error row shows the first paragraph of a reason as the error and the rest in a muted, scrollable code block.

Resume after a crash keeps the local loss. Codex 0.160.1 reloads a turn whose process died as `interrupted`, so a native `interrupted` status never replaces a local Lost turn and its reason. Without this rule the timeline would read "You stopped". The "could not be confirmed" banner appears only when the native history has no record of a lost turn.

Approval and user-input callbacks share one `Callback` registry keyed by request kind. Provider loss clears the lost slot's entries, and `ThreadSnapshot::expire_open_requests` expires every open request on both death paths, provider loss and startup. A new reverse-request kind adds one `Callback` variant and one loop there.

Restart happens on next use, as in T3. A submit, resume, model list, usage read, or collaboration-mode read launches Codex when none is running. `runtime/restarts.rs` spaces relaunches after consecutive failures by 0, 1, 2, 4, 8, 16, then 30 seconds. Each slot counts its own failures, so a failing sandbox agent never delays the Mac agent. A failed launch counts as a failure. A deliberate stop does not: the slot retires the epoch before the process exits, so its `Exited` signal is dropped. A process that stays up for 60 seconds resets the count. While a launch waits, the waiting thread's banner names the failure count and the remaining delay. Acceptance skips model and collaboration-mode checks while the Mac agent is not running, because its loss clears those catalogs. The turn-start path checks them after the relaunch and records a refused turn as not sent. Bot Code does not tear down idle sessions. T3's 30-minute `ProviderSessionReaper` is deliberately not ported, because T3 users attribute extra token use to it.

## Image attachments

`attachments.rs` owns `<data dir>/attachments`. `App::stage_attachment` runs outside the owner loop. It reads the image type from the leading bytes, ignoring the type the renderer sends, and accepts PNG, JPEG, GIF, and WebP up to 10 MiB. It names the file by the SHA-256 of its bytes, writes a `.part` file, and renames it into place. Staging the same bytes again returns the same `ImageAttachment` id and writes nothing, so concurrent stagers need no lock. `AttachmentId` parses only 64 lowercase hex digits, so an id cannot name a path outside the directory.

The renderer stages each image when it is pasted or dropped, and sends the returned `ImageAttachment` values with the submit. `accept_submit` puts the attachments in the receipt input, so the same operation ID with the same images returns the original turn and the same ID with other images is refused. It checks that each file exists with the recorded size, then stores the list in `Turn::attachments` in the thread snapshot. Saved turns and outstanding `lastRevert.attachments` are the references to a file. Rewind stores its recovery input in the same transaction that truncates the turns. The next accepted local send clears `lastRevert` in its acceptance transaction; refused or failed saves preserve it. An exact old rewind receipt returns current state without restoring consumed input. `turn/start` sends the text item, then a `localImage` item with each file's absolute path. Codex reads the files itself, so the request size does not grow with the images. The renderer keeps one operation ID while the thread, text, and images of a failed send stay unchanged.

`App::open` deletes files that neither a saved turn nor an outstanding rewind references once they are 24 hours old, and `.part` files after an hour. Archived threads count in both reference sets. The sweep runs before the owner serves commands, so it cannot race staging. Ordinary composer edits remain in renderer memory. Outstanding rewind input is durable, so its original images survive restart and return to the composer until an accepted send or a newer rewind replaces them. Removing a recovered image does not replay it in the same thread activation; reopening the thread reconstructs the outstanding saved input. The Tauri adapter serves files through the `botcode-attachment` URI scheme. It returns 404 for a name that does not parse as `<hash>.<ext>`.

## Sandbox containers

A worktree checkout can name a sandbox, `Checkout::Worktree { sandbox: Some(Sandbox::Docker { id }) }`. The worktree on the Mac stays, so cleanup, naming, restore and leases treat a sandbox checkout as a worktree. Snapshots saved before sandboxes existed load with no sandbox and save unchanged. `SandboxId` is the only stored sandbox fact. It parses only 12 lowercase hex digits, because container names, label filters and the git transport interpolate it.

`sandbox.rs` owns Docker and knows nothing about threads, git or Codex. It resolves the CLI from `BOT_CODE_DOCKER_BIN`, then the `vcs.rs` directories, then `~/.docker/bin` and Docker Desktop's bundle. It runs the CLI without a shell and puts the CLI's own directory first on `PATH`, where Docker Desktop keeps its credential helpers. `Docker::status` never fails. It reports Docker as missing, not running, or ready with its version and memory, because the composer shows the result.

Everything else derives from the id, the data directory and an instance hash. The instance is the first 8 hex digits of the SHA-256 of the canonical data directory. A container is named `botcode-<instance>-<id>` and labelled `dev.botcode.instance`, `dev.botcode.sandbox` and `dev.botcode.image`. Listing filters on the instance label, so a run with its own `BOT_CODE_DATA_DIR` never sees or touches another run's containers. The only mount is `<data dir>/sandboxes/<id>/codex-home` at `/codex-home`. It survives container removal, so a recreated container resumes the same Codex sessions. No worktree, `.git` directory or attachment is mounted. The only published ports are the desktop's 6080 and the gateway's 6081, each on a random loopback port of the Mac that Docker picks again at each start, so `Container::published` reads them from Docker each time.

The image is `botcode-sandbox:<version>`. The version is the first 12 hex digits of the SHA-256 of the embedded Dockerfile, the in-image scripts, the desktop page, the browser tool configuration and the host Codex version. A change to any of them names a new image, and containers built from an older one report as stale. `Docker::image` checks for the tag first and builds only when it is missing, one build at a time. The image is Ubuntu 24.04 with the usual build tools, Node.js LTS, the desktop stack described under "Sandbox desktop" and `@openai/codex` at the host's version, and it runs work as the non-root `botcode` user. The desktop layer comes before Codex, so a Codex update does not download Chromium again. Measured on arm64, the image is 726 MB compressed and 2.7 GB on disk, up from 376 MB and 1.49 GB without the desktop.

`Container::converge` takes a desired state, `Running`, `Paused`, `Stopped` or `Removed`. Under a per-sandbox lock, it inspects the container, runs the steps the pure `plan` returns for that pair, and returns the state Docker then reports. Running it twice does nothing the second time, and a crash between steps re-plans from what Docker reports. It never replaces a stale container, because that needs a mirror pull first. An unreachable daemon becomes `docker_not_running` with wording for the banner. The pure `reconcile_plan` decides startup repair. A referenced container that is running or paused is pulled and stopped. A container no checkout references is removed.

Killing a `docker exec` client leaves the processes it started running. Every exec therefore goes through `/opt/botcode/bin/run`. In lifeline mode, the command runs in its own process group with `/dev/null` as stdin. The wrapper stops that group when the exec's stdin closes, so a host timeout, an output overflow or a killed client also stops the work in the container. `Container::run` bounds output at 4 MiB per stream and keeps a lifeline client's stdin open until the command exits. The agent is the one exec that needs its stdin: `/opt/botcode/bin/agent` stops the group of the previous agent this container recorded, runs `codex app-server` with `CODEX_HOME=/codex-home` in its own group over the exec's stdio, and stops that group when Codex exits on stdin EOF. `Codex::terminate` therefore stays the same for both environments: it kills the `docker exec` client, and the container cleans up.

The Codex version the image installs is read from the host binary on first use, never at startup. `Docker::image` resolves it, so `App::open` does not wait on `codex --version`, and a Mac without Codex reports "Install Codex on this Mac before starting a sandbox." when a sandbox is first needed.

## Sandbox threads

`NewCheckout::Sandbox { base, fromOrigin }` creates a worktree exactly like a worktree thread and marks it `Sandbox::Docker` with a fresh id. `App::create_thread` first asks `App::sandbox_availability`, which the composer's **Run on** menu shows through the `sandbox_availability` command: `Ready { memoryBytes, lowMemory }`, with low memory below 8 GiB, or `Unavailable { reason }` when Docker is not installed, Docker Desktop is not running, or this Mac is not signed in to Codex. Creation then warms the sandbox in the background, so the first message does not wait for the image build and the seed. `NewCheckout::Existing` on a sandbox thread copies the checkout, sandbox included, so both threads share one container and one agent.

`workdir.rs` holds the one match from a checkout to where it lives. `Owner::workdir` resolves a thread to `Workdir::Mac { root }` or `Workdir::Sandbox { root, handle }`, and everything below dispatches on that value rather than on the checkout. `root()` is always the Mac path, so leases, holds, Files, Diff, search and cleanup key on it unchanged. `runtime/sandboxes.rs` keeps one `SandboxHandle` per sandbox id, created on first use from the checkout and shared by the App and the owner loop. The handle owns the container, the mirror, a flight lock, a `Phase` and an activity record. The phase is what this process last made of the container, `Starting`, `Running`, `Paused` or `Stopped`; Docker stays the authority, and a handle nobody touched reads `Stopped`. `ready` converges to a running, seeded container on the current image, pulling a stale container one last time before recreating it; it is idempotent and runs at creation, at every agent launch, before every write and when a terminal or the Desktop starts. `wake` is the cheap form for paths that run often: it takes the flight lock, so it waits for a pause in flight and undoes it, and it costs no Docker call while the phase is `Running`. Every turn on a sandbox thread and every terminal write or attach goes through it. `retire` pulls, starting a paused or stopped container first when it is about to be removed, then converges to the desired state, so the mirror is exact whenever the container is not running; a failed pull leaves the container where it is and reports. Only a `Running` handle pulls for reads; paused and stopped sandboxes serve the exact mirror.

Startup reconciliation runs in the background from `App::open`. `reconcile_plan` over this instance's containers pulls and stops a referenced container a crash left running or paused, and removes a container no checkout names together with its Codex home. It then removes `botcode-sandbox` images other than the current version that no container of any instance was created from, which `Docker::image` also does after a build; with one tag or none it stops after the `image ls`, so a start without old images never probes `codex --version`. Shutdown stops every agent slot, then pulls and stops every container this process started, paused ones included.

## Sandbox lifecycle

`workdir/idle.rs` is the idle rule, a pure function over an `Activity` record. The record holds the last instant each condition held: `touched`, the last use through Bot Code; `busy`, the last owner tick at which a thread of the sandbox had a running turn, an open approval or question, or a hold on its checkout; `cpu`, the last probe interval at or above 5% of one CPU; `desktop_client`, the last probe that found a Desktop tab connected or the last Desktop open; and `forwarded`, the last instant a connection through one of the sandbox's local server forwarders was open. While `forwarding`, the count of such connections, is above zero, the sandbox is in use. `desired(now, limits)` returns `Running`, `Paused` after `pause_after` of nothing, or `Stopped` after `stop_after`. `desktop_idle` is true when the desktop runs and no tab was connected and no turn ran for `desktop_idle`; terminal input does not count, because the shell does not use the screen. `Limits::DEFAULT` is 10 minutes, 2 hours and 3 minutes. `BOT_CODE_SANDBOX_PAUSE_AFTER_SECS`, `BOT_CODE_SANDBOX_STOP_AFTER_SECS` and `BOT_CODE_SANDBOX_DESKTOP_IDLE_SECS` override them in seconds for verification only, and the probe cadence follows at a twentieth of the pause window, between 2 s and 30 s, so an override has to leave a few seconds for the desktop window and the pause.

The owner evaluates the rule on its tick, once a second, for every started sandbox. It marks the record busy, claims the handle for one piece of work at a time, and spawns that work off the loop: a probe, a desktop stop, or an idle retire to `Paused` or `Stopped`. The probe runs the in-image `probe` script, which prints the container's cumulative CPU time from its cgroup and the number of established connections to the VNC port, so two probes give the interval's CPU share, which catches dev servers, builds and terminal jobs that no Bot Code entry point sees. Measured in the image, an idle container uses 0.02% CPU, a probe costs 12 ms including its exec, and the terminal label poll about 8 ms per second while a terminal is shown; with a live agent and a shown terminal the container reads 2.1 to 2.4%, which is why the threshold is 5% rather than 1%. A stop plans the agent slot's stop first and loses the slot's threads with "Sandbox stopped while idle. Your next message restarts it.", so idle threads become Unavailable without a banner and the next message relaunches. A pause keeps the agent live: measured with Codex 0.162.0 in the image under Docker Desktop 29.7, `codex app-server` survived `docker pause` for 630 seconds with the same pid and the same native thread, and served the next turn 5.5 seconds after `docker unpause`. The idle retire re-checks under the flight lock that nothing touched the sandbox since the rule decided, so a wake in between wins. A failed retire keeps the container and counts as a touch, so the next attempt waits a full window. When a retire changes the container's state, a `SandboxChanged` completion sends a change hint for each of the sandbox's threads, and the renderer reads `sandbox_state` again for the composer strip.

Opening a sandbox thread while its container is paused or stopped does not resume the agent, unlike opening an unavailable Mac thread: the open is a read, and the next message starts the container and relaunches. Settle and archive ask the handle for a stop, which the next tick performs once no thread of the sandbox is busy, with "Sandbox stopped. Your next message restarts it."; any use before that withdraws the request. Unsettle and unarchive do nothing. Deleting the last thread of a sandbox stops its agent, pulls the mirror one last time, removes the container and deletes `<data>/sandboxes/<id>`, and only then commits the deletion, so a failed final pull keeps the thread, the container and the Codex home and returns `sandbox_kept` with the reason. The storage sweep's `ClaimCleanup` returns the candidate's sandbox handle after stopping its agent; the sweeper retires the container with a final pull, keeping the Codex home, before `git worktree remove`, and a failed pull keeps the worktree. The next message on such a thread restores the worktree, and `ready` creates a container from it and resumes the kept Codex sessions.

Agent paths map both ways through `AgentPaths`. Outbound, a sandbox thread's `cwd` for `thread/start`, `thread/resume` and `thread/fork` is `/workspace`, and each attachment is copied into `/botcode/attachments/<name>` before `turn/start` or `turn/steer`, through the agent user's own `cat`, so the prompt note and the `localImage` item name that path. Skills keep the Mac. Inbound, `/workspace/<rel>` and relative paths map to the mirror; any other absolute path from a sandbox agent is a container path, which an image view fetches out of the container with a 4.4 MB cap and a chat link refuses, because it has no copy on this Mac. A Mac path named by a sandbox agent never resolves on the Mac.

Codex's own sandbox does not work inside Docker's default profile. Measured with Codex 0.162.0 in the image under Docker Desktop 29.7 (kernel 7.0.12-linuxkit): `codex sandbox` with `workspace-write` or `read-only` fails with "bwrap: No permissions to create a new namespace", and only `--security-opt seccomp=unconfined` lets bubblewrap work. The container is therefore the boundary. A sandbox thread's `thread/start` and `turn/start` send `danger-full-access` whatever the permission mode says, and keep the mode's approval policy and reviewer, so Supervised still asks before commands and Auto still reviews them. Sandbox agents always register the PR tools dynamically on their first `thread/start`, whatever the desktop's registration is, and never the host preview backend, which cannot reach into a container. A tool call from a sandbox agent decodes against that catalog, so a preview tool name is unknown to it.

`codex/auth.rs` is the token broker. It reads the host `auth.json` from `$CODEX_HOME` or `~/.codex` into typed credentials whose secrets are redacted in Debug and never serialized: ChatGPT tokens with the account id and the plan type from the id token's claims, or an API key. A missing file means the Mac is not signed in. Login sends `account/login/start { type: "chatgptAuthTokens", accessToken, chatgptAccountId, chatgptPlanType }` or `{ type: "apiKey", apiKey }`. When a sandbox agent sends `account/chatgptAuthTokens/refresh`, the owner answers off its loop: the broker asks the live Mac agent `account/read { refreshToken: true }`, or a throwaway host app-server when the Mac agent is not running, then re-reads the file. Refreshes that start within five seconds share one result. A refresh whose `previousAccountId` differs from the host's current account is refused with a JSON-RPC error, so a Mac account switch never leaks into a running sandbox. The refresh token stays in the Mac's file, and no token is written into a sandbox's Codex home or a log. A refresh request from the Mac agent itself is refused as unsupported.

Reads go through `App::checkout`, which pulls the mirror with `Freshness::Recent` first and serves the stale mirror when the pull fails. Mutating host functions take a `WriteRoot`: `repo::write_file`, `repo::switch_branch`, `checkpoints::restore` and the naming rename. Only `WriteRoot::mac` and a mirror `WriteSession` produce one, so a sandbox mutation that forgets the push does not compile. `Workdir::write` runs one blocking mutation inside a session and pushes afterwards, even when the mutation failed, so a partial write still reaches the container. A push refusal surfaces as `sandbox_diverged` or `sandbox_blocked`. Background source-control refresh skips sandbox checkouts, because a Mac-side fast-forward would bypass the session; the user's Pull action runs inside one.

A turn on a sandbox thread keeps the Mac ordering with the mirror added. Acceptance takes the lease. The before capture holds `sync(Exact)` through `checkpoints::capture` on the mirror, so a UI read's pull cannot rewrite the worktree under it. The capture persists, the attachments are copied in, and `turn/start` goes out. On `turn/completed` the after capture holds the same guard through the capture and the file list. Rewind runs `checkpoints::restore` inside a write session under the existing `Hold::Revert`; a push refusal fails the RestoringFiles phase, and Retry revert runs it again. Branch naming renames on the mirror with every Mac-side check, then renames in the container, and ends with a pull so both sides agree; a container failure undoes the Mac rename.

Git actions run inside a write session. Status, planning, staging and `checkout -b` work on the mirror as before. The commit runs in the container through `WriteSession::commit`, so repository hooks use the container's toolchain, and the pull afterwards brings the commit back. The session ends before the network steps, and push, pull and `gh pr create` run on the Mac mirror with the Mac's credentials, unchanged. A commit on a sandbox thread streams no hook progress; it reports the landed commit and the hook output as before.

`App::open_target_path` refuses a sandbox checkout with `sandbox_mirror`, so no editor or file manager opens the mirror. The renderer hides Open in and Reveal in Finder from `checkout.sandbox`.

A terminal starts from a `terminal::Launch`, which `Workdir::terminal` picks. `Mac { cwd }` runs the configured shell as before, and `Sandbox { container }` first calls the handle's `ready`. While a handle this process has not readied gets ready, `App::terminal_attach` sends "Starting sandbox…" as terminal output, and a failure returns the reason. The sandbox PTY runs a `docker exec --interactive --tty` client for the in-image `terminal shell <id>` script, which records its pid under `/dev/shm/botcode-terminals/<id>` and execs `bash -l` as `botcode` in `/workspace`. Only `TERM` and `COLORTERM` cross into the container. The Docker client keeps the Mac environment it needs for its own configuration.

Killing a `docker exec --tty` client, or closing its PTY, leaves the shell, its foreground job and its background jobs running, and nothing in the container sees the client go, as measured with Docker Desktop 29.7. The terminal's pump therefore runs `terminal stop <id>` when the client ends for any reason. The script hangs up every process in the shell's session and kills what is left a second later. Closing a terminal or its tab, deleting the thread and quitting all end the client, so they all stop the session. After a crash, startup reconciliation stops the container.

The label poller reads a sandbox shell's command with one `terminal ps` exec per container per poll, which prints the registered shells and the container's process table. It skips containers whose terminals have no subscriber and keeps their last labels, and it keeps a source's labels while that source cannot be read, with the existing back-off. The shell prints OSC 133;A before each prompt. When the pump sees it, it sends the terminal's key to `runtime/sandboxes.rs`, which waits until the thread's terminals have been quiet for one second, pulls the mirror with `Freshness::Recent`, and has the owner send a `refreshWorkspace` hint. The wait matches the Recent window, so a pull from before the command's edits never stands in for a new one. Project scripts on a sandbox thread run `bash -c` in that shell with `/workspace` in both `T3CODE_PROJECT_ROOT` and `T3CODE_WORKTREE_PATH`.

Worktree setup for a sandbox thread runs in the container. The setup stays Pending until the handle is ready, warming it if nothing else does, and then the Mac wrapper that records the pid and the receipt runs the submodule checkout and the script through a lifeline exec. Bot Code holds the wrapper's stdin, so stopping the wrapper or quitting ends the work in the container too.

## Sandbox desktop

A sandbox has a Linux desktop that the Desktop tab shows and the agent's browser drives. TigerVNC's `Xvnc` serves display `:1` and resizes when a client asks through ExtendedDesktopSize. `matchbox-window-manager` gives the focused window the whole screen. `websockify` serves the desktop page and noVNC 1.7 from npm and proxies its websocket to VNC on the container's loopback. Ubuntu's `chromium` package is a snap that does not run in Docker, and Google Chrome has no arm64 Linux build, so the browser is Playwright's Chromium, installed with its system libraries.

Nothing starts the desktop with the container. The in-image `desktop start` script starts whichever of the X server, the window manager and the proxy is not running, under a lock, each in its own session so the lifeline exec that ran it does not take it down, and waits until the VNC and websocket ports answer. Running it again starts nothing. Its state lives in `/dev/shm/botcode-desktop`, which a container restart empties with the processes. Measured with Docker Desktop 29.7, a first start takes about 0.2 s and a repeated one about 0.07 s, and the idle desktop holds 67 to 71 MiB resident with no client connected: about 25 MiB for `Xvnc`, 11 MiB for the window manager and 30 to 37 MiB for `websockify`.

One secret gates the desktop. `websockify` takes it as the websocket token, so without it the proxy closes the connection before VNC answers, and `Xvnc` takes its first 8 characters as the VNC password. `SandboxHandle` makes the secret from a random UUID when the handle is created and keeps it only in memory. `App::sandbox_desktop` readies the container, runs `desktop start --secret-stdin` with the secret on stdin, so it is never in an argument, a label, a log or the agent's environment, and returns the published port and the secret. The script rewrites the password and token files at every start, so the Desktop tab's secret also replaces one from an earlier run or from a start the agent caused. The proxy's own log would name the token, so its output is discarded.

The agent's browser tools are `@playwright/mcp` 0.0.83, registered as the `browser` MCP server by `-c` overrides on `codex app-server` in the in-image `agent` script, with every tool approved like Bot Code's own tools. The overrides travel with the image version instead of a file Bot Code would have to merge into the sandbox's Codex home. The server launches Chromium headed through the in-image `browser` script, which starts the desktop first and runs Chromium on `:1` with no fixed viewport, so pages follow the window and the window follows the Desktop tab. Snapshots and screenshots without a file name go to `~/.cache/playwright-mcp`, outside `/workspace`, so they never reach the mirror. Sandbox agents still never get the Mac preview tools.

The desktop also stops: `desktop stop` kills `Xvnc`, the window manager, `websockify` and Chromium, and the owner runs it when the idle rule finds the desktop running with no tab connected and no turn for about 3 minutes. An animated page in a hidden Chromium measured about 14% CPU, which would otherwise block every pause. `desktop clients` counts the established connections to the VNC port, one per connected tab, and the `probe` script reports it with the CPU counter.

Containers created by slice 2 and 3 images lack the published port. Their image label differs from the current version, so `ready` pulls them and recreates them with the port.

## Sandbox local servers

A dev server in a sandbox usually binds `localhost`, and Vite binds only `::1`. Docker publishes only ports bound to the container's network address, and only the ports named at create, so it cannot publish such a server. The in-image `gateway` relays to the container's loopback instead, and Docker publishes its port 6081 on a random loopback port of the Mac. Nothing starts the gateway with the container. `SandboxHandle` starts it on first use with `gateway start`, which takes a secret on stdin, writes it to `/dev/shm/botcode-gateway/token`, starts the relay in its own session unless one runs, and waits until it listens. Running it again starts nothing and only rewrites the token. The relay reads the token for each connection, so a start with a new secret takes effect at once. The secret is a random UUID that the handle makes when it is created and keeps only in memory, separate from the desktop's, so it is never in an argument, a label, a log or the agent's environment.

Each gateway connection starts with one line, `<token> <port>\n`. The relay checks the token in constant time, connects to `127.0.0.1:<port>` and then `[::1]:<port>`, and pipes bytes both ways. A wrong token, a malformed line, a line not sent within 10 seconds or a refused target closes the connection without a byte. `sandbox::dial` writes that line, and the handle caches the gateway's published port until the container stops or a probe finds the gateway not listening.

`workdir/forward.rs` holds the Mac side. `SandboxHandle::forward(port)` binds a tokio listener on `127.0.0.1:0` the first time a container port is needed and returns its port, which stays the same until the container stops. Each accepted connection counts in the activity record while it is open, wakes the container through `wake`, opens a gateway connection and copies both ways. A connection to a paused container therefore unpauses it, and an open page with a hot-reload socket keeps the sandbox running. `retire` to `Stopped` or `Removed` drops every listener, which aborts its accept loop and the open connections with it, forgets the gateway port and empties the server list. A forwarder costs one listener and one task per open connection on the Mac, and the relay is one Python process of about 19 MB in the container.

The `probe` script also prints the LISTEN rows of `/proc/net/tcp` and `/proc/net/tcp6`, because the image has no `ss`. `sandbox::listening_ports` keeps the rows whose address `localhost` reaches, a loopback or unspecified address, and `Probe` leaves out VNC's 5900, noVNC's 6080 and the gateway's 6081. Every probe, from the idle tick or from discovery, records the list on the handle, so a paused container still reports the servers it had. A stopped one reports none, because its servers stopped with it.

`App::local_network(thread)` returns `LocalNetwork::Mac` or `LocalNetwork::Sandbox`, whose `listeners`, `dial` and `forward` are the only way the app crate reaches a container's servers. `listeners` probes a running container and otherwise reports the last list without waking it. `dial` opens a gateway connection that neither wakes the container nor counts as use, for discovery. `src-tauri/src/preview/route.rs` is the one mapping from a conversation's network and a URL to the URL to load. On a Mac thread, a draft or the Desktop tab, every URL loads as it is. On a sandbox thread, a URL whose host is `localhost` or a loopback address loads from `http://127.0.0.1:<forwarder>` with the same path, query and fragment, and its `Alias` maps addresses the page reports back to the container address.

Preview's open, Reload after an error, a page's request for a new window, a chat or terminal link opened in Preview, and a project script's `previewUrl` all go through `PreviewManager::open_url`, which applies the mapping. The entry keeps the alias, so the page-load and refresh paths store the container address in the URL field. Readiness for a forwarded URL waits up to 5 seconds for the port to appear in the container's listeners instead of connecting on the Mac. A forwarded view closes when its Preview is detached, whether by another tab, a closed panel or another thread, and keeps its URL; the next attach loads it again, which wakes the container. Without that, a hidden page's hot-reload socket would keep the sandbox from pausing. `open_url` for the system browser takes the link's thread and opens the forwarded address, because the browser runs on the Mac. `preview_discover` takes the scope. For a sandbox thread it lists the container's listeners, reads each running one's page through `dial` with the same HTML and opt-out rules as on the Mac, and returns `http://localhost:<port>/` with the page title. A paused container's servers are listed untitled without being read, because a read would wait on the frozen relay. Mac discovery leaves out every forwarder's port, which `App::forwarder_ports` lists, because those are a sandbox's servers and a probe through one would keep the sandbox awake.

Measured with Docker Desktop 29.7 on arm64 in the spike, a Vite app bound to `::1` loaded in 104 ms through the gateway with hot reload working, against 201 ms for a `docker exec` tunnel per connection and 93 ms for fixed published ports. Through the shipped forwarder, the 17 requests of a new Vite 8 React app's module graph, each on a new connection, took 94 ms the first time and 74 ms after. A forwarded connection to a paused container answered in 112 ms, including the unpause.

## Reconciled design choices

Candidate A supplied the owner loop, shared provider, execution leases, and delivery model. Candidate B supplied caller operation receipts and simple snapshot invalidation. The independent review added canonical-root exclusion, revision guards, storage-failure rollback, bounded stdin writes, old-response ordering, and process-group cleanup.

Full event sourcing, generated protocol types, a frontend patch/replay framework, eager provider restart without a pending request, universal paginated history hydration, and filesystem watchers remain deferred. The current native resume is verified against installed Codex 0.160.0. A newer protocol can require changes in the private decoder.

Core tests and the real Codex smoke exercise the Tauri-independent App API. Typechecking and frontend/native builds verify package integration. The actual Tauri window passed interaction checks for folder selection, two repositories, Pierre file/diff rendering, streamed Codex output, command and file approvals, interruption, renderer reload with a live approval, and history continuation after a full application restart. These checks used disposable repositories and isolated Bot Code state.
